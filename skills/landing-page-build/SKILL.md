# 🏭 สายการผลิตแลนดิ้งเพจ (Landing Page Build)

สกิลนี้คือ **"ทำยังไงให้เสร็จจริงและไม่พัง"** ไม่ใช่ "เขียน copy ยังไงให้ขายได้"

| สกิล | รับผิดชอบ |
|---|---|
| `landing-page-craft` | ใครคือคนอ่าน · พาดหัว · ลำดับ section · conversion · honesty guard |
| **`landing-page-build`** (ตัวนี้) | เตรียมของ · mockup · โครง CSS · ตรวจด้วยการวัด · ขึ้น prod |

เริ่มงานใหม่ให้อ่าน `landing-page-craft` ก่อนเพื่อฟิกซ์โครงกับ copy แล้วค่อยกลับมาที่นี่

**หลักคิดที่คุมทั้งสกิล:** หน้า landing พังจาก *เรื่องเล็กที่มองด้วยตาไม่เห็น* มากกว่าพังจากดีไซน์ — ข้อความล้นขอบจอ 3px, คำโดดบรรทัดเดียว, รูปทับตัวอักษร, ลิงก์ footer ชี้ไป 404 · ทุกเฟสด้านล่างจึงจบด้วย **การวัด ไม่ใช่การมอง**

## เฟส 0 — เตรียมของให้ครบก่อนเริ่ม

ถ้าของไม่ครบ จะเจอ "ทำไปแก้ไป" ซึ่งกินเวลามากกว่าเตรียมล่วงหน้าหลายเท่า **ไล่เช็คลิสต์นี้กับผู้ใช้ก่อนแตะโค้ด**

### ก. เนื้อหา
- [ ] **copy ทุกคำ** — จาก `landing-page-craft` (พาดหัว · sub · pain · ฟีเจอร์ · FAQ · CTA label)
- [ ] **ข้อความในภาพประกอบต้องตรงกับของจริงในระบบ 100%** — ถ้าโชว์การ์ด/ข้อความบอท ให้ไปลอกจากไฟล์ที่ระบบใช้จริง (เช่น `lib/line/flex.ts`, ข้อความ cron) · โชว์ของที่ระบบทำไม่ได้ = โกหกลูกค้า
- [ ] **ตัวเลขทุกตัวต้องเป็นของจริง** — ส่วนลด % ต้องคำนวณจากกติกาจริง · จำนวนสิทธิ์คงเหลือต้องมีที่มา · ห้าม fake anchor (ขีดฆ่าราคาที่ไม่เคยเก็บจริง)

### ข. ภาพและ asset
- [ ] **ตัดสินก่อนว่าจะใช้ "หลักฐาน" แบบไหน** — ⚠️ **สกรีนช็อตจากระบบจริงมักมีข้อมูลส่วนบุคคล** (ชื่อคน รูปโปรไฟล์ ข้อความในกลุ่ม) เอาขึ้นเว็บสาธารณะ = ขัดกับนโยบาย PDPA ที่ตัวเองประกาศ → **ทางออกที่ดีกว่าคือประกอบ "จอจำลอง" ด้วย HTML/CSS** ใช้ถ้อยคำจริงแต่ข้อมูลสมมติ · มือถืออ่านออกกว่า แก้ง่ายกว่า ไฟล์เบากว่า และเอามาสคอตมาคาบขอบได้
- [ ] **มาสคอต/ภาพประกอบ** — เตรียมเป็นไฟล์เว็บ (WebP) ที่ 2× ของขนาดแสดงผล · **ครอปให้ subject สูงเท่ากันทุกใบ** (ดูกับดัก #3)
- [ ] **โลโก้ · QR · ไฟล์รูปที่ผู้ใช้ต้องวางเอง** — รูปที่แปะมาในแชทเซฟเป็นไฟล์เองไม่ได้ ต้องขอให้ผู้ใช้วางลงโฟลเดอร์
- [ ] **ปลายทาง CTA จริง** + ตัวแปร env ให้ override ต่อ deploy ได้

### ค. หน้าที่ต้องมีอยู่ก่อน footer จะลิงก์ไปได้
- [ ] `/privacy-policy` · `/terms` · `/security` (หรือเท่าที่ธุรกิจต้องมี)
- [ ] **ห้ามใส่ลิงก์ใน footer ก่อนหน้าปลายทางมีจริง** — ลิงก์ตาย 1 เส้นทำลายความน่าเชื่อถือทั้งหน้า
- [ ] เนื้อหาหน้ากฎหมายดูเช็คลิสต์ PDPA ท้ายสกิล

### ง. เทคนิค
- [ ] **CSS อยู่ที่ไหน** — หน้า landing มัก bespoke ทั้งหน้า ถ้า repo ใช้ Tailwind อยู่ **ไม่ต้องฝืนแปลง** เขียน CSS ไฟล์เดียว scope ใต้คลาสราก (เช่น `.lp`) จะคุมง่ายกว่าและไม่รั่วไปหน้าอื่น · บอกเหตุผลไว้ในหัวไฟล์
- [ ] **ฟอนต์มีน้ำหนักอะไรบ้าง** — เช็คก่อนใช้ (IBM Plex Sans Thai มีถึง 700 ไม่มี 800 · ใส่ 800 แล้วเบราว์เซอร์จะปลอมให้ ดูเบลอ)
- [ ] **ภาษาไทยตัดบรรทัดต่างจากอังกฤษ** — ไม่มีเว้นวรรคระหว่างคำ เบราว์เซอร์ตัดตรงรอยต่อคำที่มันรู้จัก ทำให้เกิดคำโดดบรรทัดเดียวง่ายมาก (ดูกับดัก #4)

## เฟส 1 — วางแผน

1. อ่าน `landing-page-craft` → ฟิกซ์โครง section + copy
2. เขียน **สเปกลงไฟล์** ในศูนย์เอกสาร (`0_public_eco_doc_claude/docs/<ชื่อ>-spec.md`) ไม่ใช่เก็บไว้ในหัว — งาน landing ยาวหลาย session
3. **กันลายเซ็น AI:** อย่าให้ทุก section เป็น "การ์ดเท่ากัน N ใบ" · แบ่งเป็นตัวเด่น 2 + ตัวกระชับ 4 หรือใช้ผังไม่สมมาตร (2-1-1-2)
   - ⚠️ **ผังไม่สมมาตรมีต้นทุน:** ช่องแคบต้องการข้อความสั้น ถ้ามีข้อความสั้นไม่พอ จะมีข้อหนึ่งตกบรรทัดเสมอ → นับความยาว copy เทียบจำนวนช่องแคบ **ตั้งแต่ตอนวางผัง**

## เฟส 2 — Mockup ก่อนลงโค้ดจริง

**โชว์ mockup ก่อนเสมอ** ผู้ใช้ตัดสินใจจากภาพได้เร็วกว่าจากคำอธิบายมาก และถูกกว่าการโค้ดผิดแล้วรื้อ

- ใช้ **HTML wireframe แบบกล่องเส้น** (ยังไม่ลงสี) เผยแพร่เป็น artifact ให้กดดูได้
- **เจอจุดที่ตัดสินใจยาก → เสนอ 2–3 แบบเทียบกัน** พร้อม *ต้นทุนของแต่ละแบบ* แล้วเชียร์ 1 แบบพร้อมเหตุผล อย่าโยนตัวเลือกเปล่าๆ ให้ผู้ใช้เลือกเอง
- **โชว์ "สภาพตอนนี้" เป็นกล่องแรกด้วย** พร้อมไฮไลต์ปัญหา (เช่น แรเงาพื้นที่ว่างที่เสียเปล่า) — ผู้ใช้จะเห็นทันทีว่าเรากำลังแก้อะไร

## เฟส 3 — ลงโค้ด

### ปุ่มเดียวคุมจังหวะทั้งหน้า
ระยะห่างแนวตั้งคือสิ่งที่ถูกขอให้ปรับบ่อยที่สุด **อย่าใส่ค่าคงที่กระจายทั้งไฟล์** ประกาศ token กลางไว้ 2 ตัว แล้วใช้ทุกที่:

```css
.lp{
  --band:clamp(28px,3.6vw,48px);    /* ระยะบน-ล่างของแต่ละบล็อก */
  --bandgap:clamp(22px,3vw,34px);   /* ระยะภายในบล็อก */
}
.lp .band{padding-block:var(--band)}
```

ผู้ใช้บอก "ยาวไป" → แก้ 2 บรรทัด ไม่ใช่ไล่แก้ 40 จุด · **ค่าที่ตอบสนองความกว้างจอ (`clamp`) ทำให้มือถือกับเดสก์ท็อปพอดีคนละค่าโดยไม่ต้องเขียน media query**

### ไต่บันไดก่อนหยิบ JavaScript
ปุ่มสลับ/แท็บ/accordion ส่วนใหญ่ทำด้วย CSS ล้วนได้ — `<input type="radio">` ซ่อน + `:has()` บนบรรพบุรุษร่วม:

```css
.lp .price.mo{display:none}
.lp #pricing:has(#bill-month:checked) .price.yr{display:none}
.lp #pricing:has(#bill-month:checked) .price.mo{display:flex}
```

ได้ของแถมฟรี: **ไม่ส่ง JS เพิ่มสักไบต์** · หน้ายังเป็น static · คีย์บอร์ดและ screen reader ใช้ได้เองเพราะเป็น radio จริง · ไม่มี hydration ให้พัง

### รูปประกอบที่ไม่กินพื้นที่
ภาพคนยืน/มาสคอตมักสูงกว่ากว้างราว 1.8 เท่า **การเอาไปคร่อมขอบแนวนอนตรงๆ จะดันตัวเองขึ้นไปทับข้อความข้างบนร่วม 150px** · ถ้าอยากให้ลอยโดยไม่กินความสูง ให้ **ตรึงมันไว้ในช่อง (gutter) ด้านข้างของกล่องข้างเคียง** แล้วเว้นระยะ padding ฝั่งนั้นให้เนื้อหาหลบ

### สีเชิงความหมาย ≠ สีแบรนด์
ป้าย "ประหยัด 17%" ใช้เขียวไม่ใช่สีแบรนด์ — เพราะสีแบรนด์เป็นสีของปุ่มกด ถ้าใช้สีเดียวกันป้ายจะไปแย่งสายตากับ CTA

## เฟส 4 — ตรวจด้วยการวัด ไม่ใช่ด้วยตา

**นี่คือเฟสที่แยกงานเสร็จออกจากงานที่ดูเหมือนเสร็จ** เปิด preview server แล้วรัน `scripts/audit-page.js` (อยู่ในสกิลนี้) ผ่าน `javascript_tool` — มันเช็คให้ครบรอบเดียว

จุดที่คนพลาดบ่อยที่สุด: **กล่องของ element ≠ ตัวอักษรจริง** · `.desc` เป็น block กว้างเต็มคอลัมน์เสมอ ต่อให้บรรทัดสุดท้ายมีคำเดียว · เช็คการทับกันด้วย `Range.getClientRects()` ซึ่งคืน **กล่องของแต่ละบรรทัดจริง** ไม่ใช่กล่อง element:

```js
const lineRects = el => { const r = document.createRange(); r.selectNodeContents(el); return [...r.getClientRects()]; };
```

**ต้องผ่านทุกข้อก่อนถือว่าเสร็จ:**
- [ ] `scrollWidth - clientWidth === 0` ทั้งที่ **390 / 768 / 1440** (จอแคบสำคัญสุด)
- [ ] ไม่มีรูปทับตัวอักษรจริงสักจุด (วัดด้วย line rects)
- [ ] ไม่มีบรรทัดสุดท้ายที่สั้นกว่าบรรทัดยาวสุด 25% (= คำโดด)
- [ ] ของที่ควรอยู่ระดับเดียวกัน ต่างกัน ≤ 2px
- [ ] ความยาวหน้าเทียบเป็น "กี่จอ" — เกิน 10 จอบนเดสก์ท็อปถือว่ายาวเกิน ให้กลับไปบีบ token
- [ ] `tsc --noEmit` สะอาด + `build` ผ่าน
- [ ] ทุกลิงก์ใน footer ตอบ 200

> ⚠️ **อย่าวัดที่ความกว้างจอเดียวแล้วสรุป** — ถ้า breakpoint 2 คอลัมน์อยู่ที่ 940px การวัดที่ 925px จะเห็นทุกอย่างเรียงซ้อนกันและ **ตัวเลขจะดูแย่กว่าความจริงมาก** วัดที่ความกว้างที่ผู้ใช้ใช้จริงเสมอ

## เฟส 5 — ขึ้น prod

1. **build ให้ผ่านก่อน push** — ห้ามข้าม
2. `.gitignore` ของเครื่องมือ (`.claude/` `.impeccable/`) ก่อน stage
3. commit แยกก้อนตามความหมาย (โค้ดหน้าเว็บ / เอกสาร / หน้ากฎหมาย)
4. **push branch แล้วหยุด** ให้ผู้ใช้เปิดและ merge PR เอง — การ merge เข้า main คือการเผยแพร่จริง
5. **หลัง merge ต้องกลับมาตรวจ prod จริง** ไม่ใช่เชื่อว่า deploy แล้วจบ

> ⚠️ **กับดักหลัง deploy:** หน้าใหม่อาจตอบ **404 อยู่พักหนึ่งเพราะแคชขอบ (edge cache) ค้างจากตอนที่ยังไม่มี route นั้น** · ก่อนจะสรุปว่าไฟล์หาย ให้ยิงซ้ำโดยต่อ `?cb=<timestamp>` ท้าย URL — ถ้าได้ 200 แปลว่าแค่แคชค้าง เดี๋ยวหายเอง

## 6 กับดักที่เจอจริง (อ่านก่อนเริ่ม จะประหยัดเวลามาก)

1. **แถบ nav แบบ sticky ทับของที่ลอยขึ้นไป** — nav มี z-index สูง อะไรที่โผล่ขึ้นไปในเขตนั้นจะถูกตัดหัว ไม่ใช่รูปขาด
2. **ฟอนต์ไม่มีน้ำหนักที่สั่ง** — เบราว์เซอร์ปลอมให้ ผลคือตัวหนาดูเบลอ เช็ครายการน้ำหนักก่อนใช้
3. **รูปชุดเดียวกันดูขนาดไม่เท่ากัน** — เพราะสั่ง *ความกว้าง* เท่ากัน แต่ไฟล์ต้นทางครอปมาสูงเท่ากันและกว้างต่างกันตามท่าทาง → **สั่งมิติที่คงที่ในไฟล์ต้นทาง** (ปกติคือความสูง) แล้วปล่อยอีกด้าน auto
4. **คำไทยโดดบรรทัดเดียว** — ใส่ `text-wrap:balance` ที่ย่อหน้าสั้นๆ ทุกอัน เป็นการแก้ที่กลไก เปลี่ยน copy ทีหลังก็ไม่กลับมาเป็นอีก · ถ้าอยากได้บรรทัดเดียวจริงๆ ให้ถอด `max-width` ออกเมื่อมี flex/grid คุมความกว้างอยู่แล้ว
5. **ตารางแบ่งช่องเท่ากันทำให้แถวดูเอียง** — ของในช่องเกาะขอบซ้ายของช่องตัวเอง ระยะที่ตาเห็นเลยไม่เท่ากัน → ถ้าต้องการ "จัดกลางทั้งแถว" ใช้ flex + `justify-content:center` อย่าใช้ grid
6. **รัน `npm run build` ทับตอน dev server ยังรันอยู่** → dev พังด้วย `Cannot find module './xxx.js'` · ไม่ใช่บั๊กในโค้ด ล้าง `.next` แล้วรีสตาร์ท

## เช็คลิสต์เนื้อหาหน้ากฎหมาย (ไทย/PDPA)

หน้ากฎหมายเป็นส่วนหนึ่งของงาน landing เสมอ เพราะ footer ต้องลิงก์ไปหา · **ให้มีโครงเดียวกับหน้าหลัก** (nav + ปุ่มกลับหน้าแรก + การ์ด + footer + ลิงก์ไขว้ระหว่างเอกสาร) หน้ากฎหมายที่หน้าตาหลุดจากทั้งเว็บทำให้ดูเหมือนของแถมที่ไม่มีใครดูแล

หัวข้อที่คนไทยมักลืมและ**ถูกจับได้**:
- [ ] **การโอนข้อมูลไปต่างประเทศ** — ถ้าใช้ Supabase/Vercel/Firebase = ข้อมูลอยู่นอกไทย ต้องแจ้ง
- [ ] **รายชื่อผู้ประมวลผลข้อมูล** — ใครแตะข้อมูลบ้าง (แพลตฟอร์ม · ฐานข้อมูล · โฮสต์ · ผู้รับชำระเงิน)
- [ ] **ฐานทางกฎหมายรายวัตถุประสงค์** — ไม่ใช่เขียน "ยินยอม" ลอยๆ ข้อเดียว
- [ ] **ข้อมูลผู้เยาว์** และ **วิธีแจ้งเมื่อนโยบายเปลี่ยน**

## บทเรียนจากสนามจริง (KruaCost · 2026-08-22)

### หน้า `/demo` กดเล่นได้จริง ดีกว่าภาพนิ่งและวิดีโอ
ถ้ามี wireframe/prototype ที่กดได้อยู่แล้ว **เอาขึ้นเป็นหน้าสาธารณะเลย** ไม่ต้องรอระบบจริงเสร็จ
- ทำเป็น **route แยก (`/demo`) ไม่ฝังในหน้า landing** — ตัวอย่างมีแถบเมนูแบบ `fixed` ถ้าฝังจะลอยทับเนื้อหา และมีเมนู 2 ชุดแย่งกัน
- **ใช้คอมโพเนนต์เดียวกับตัว prototype ส่ง prop `mode` เข้าไป** อย่าก๊อปโค้ดสองชุด ไม่งั้นแก้ที่เดียวอีกที่ไม่ตาม
- ได้ผลพลอยได้ที่มีค่ามาก: **ส่งลิงก์ให้คนหน้างานกดจากมือถือได้ทันที** ไม่ต้องนัดเปิดคอม ไม่ต้องสร้างบัญชีให้

### ตัวอย่างที่โชว์ของที่ยังไม่มีจริง = ต้องมีแถบบอกสถานะที่ปิดไม่ได้
คนกดเล่นแล้วเห็นมันทำงานลื่นๆ จะเข้าใจว่าระบบเสร็จแล้ว
→ แถบ `sticky` บนสุด **"ตัวอย่างการใช้งาน · ข้อมูลสมมติ · บางส่วนยังอยู่ระหว่างพัฒนา"** ปิดไม่ได้ เลื่อนไปไหนก็ยังเห็น
→ ปุ่มที่ยังไม่ทำงานยังต้องบอกตรงๆ แค่เปลี่ยนเป็นภาษาลูกค้า ("ยังไม่เปิดในตัวอย่างนี้" ไม่ใช่ "ยังไม่ได้ทำ")

### ⚠️ ตัดอะไรออกจากหน้า ต้องไล่เก็บลิงก์ที่ชี้ไปหามันให้ครบ
ตัด section ฟอร์ม waitlist ทิ้ง = เหลือปุ่มกดแล้วไม่ไปไหน 4 จุด (hero · แถบ CTA · ปุ่มในจอจำลอง · ท้ายหน้า demo)
**`grep` หา anchor/href ที่ชี้ไป section นั้นก่อนลบเสมอ** แล้วลบไฟล์คอมโพเนนต์ที่กลายเป็นของกำพร้าด้วย
