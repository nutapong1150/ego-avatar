# เนตรทดสอบรอบด้าน (System Test Sweep)

## หลักการ

**"ผ่าน tsc + test + เปิดหน้าที่แก้ดูแล้ว" คือการทดสอบโค้ดที่ข้าแก้ ไม่ใช่การทดสอบระบบ**
บั๊กที่ผู้ใช้เจอจริงมักอยู่ในช่องว่างระหว่างฟีเจอร์ เช่น คำสัญญาบนหน้าจอที่ไม่มีปุ่มรองรับ ตัวเลือกที่กดแล้วไม่มีผลอะไร หรือข้อมูลที่กรอกแล้วไม่ถูกแสดงกลับที่ไหนเลย

การเลือกทำตามแค่ "เจตนา" แล้วข้ามบางชั้น ก็นับเป็นการข้ามชั้นเหมือนกัน

**ผลของสกิลนี้คือรายงาน** หยุดที่รายงาน ท่านเลือกข้อที่จะแก้ แล้วค่อยแก้ (ท่านเคาะ 2026-10-11)

## ลำดับ 9 ชั้น (ห้ามข้าม ถ้าทำไม่ได้ต้องเขียนในรายงานว่าไม่ได้ทำเพราะอะไร)

| ชั้น | ทำอะไร | สิ่งที่มักพลาด |
|---|---|---|
| 0 ขอบเขต | ระบุว่าทดสอบทั้งระบบหรือแค่ส่วนที่เปลี่ยน · ระบุ persona อย่างน้อย 2 แบบ (ผู้ใช้ใหม่ / ผู้ใช้ประจำ) และสายการใช้งานที่แตกต่างกัน | ทดสอบแค่สายการใช้งานหลักสายเดียว |
| 1 ด่านอัตโนมัติ | typecheck · lint · test · build แล้ว **เทียบกับ baseline** (tree มีไฟล์ค้างอยู่ → `git stash` แล้วรันใหม่ · tree สะอาดอยู่แล้ว → HEAD คือ baseline) · build ชนกับ dev server ที่ใช้ `.next` อยู่ → ข้ามได้ แต่ต้องเขียนในรายงาน | บอกว่า "error มีอยู่ก่อนแล้ว" โดยไม่ได้พิสูจน์ |
| 2 ตาราง CRUD | ทุก entity ต้องมีคำตอบครบ: สร้าง / ดู / แก้ / ลบ / ดูย้อนหลัง · ช่องไหนไม่มี ต้องบอกได้ว่าตั้งใจไม่ทำ | ลบไม่ได้ · ดูย้อนหลังไม่ได้ |
| 3 ตรวจคำสัญญา | grep ข้อความในหน้าจอ / PDPA / ToS / onboarding ที่พูดถึงความสามารถ ("ลบได้", "แจ้งเตือน", "เห็นเฉพาะท่าน") → จับคู่กับปุ่มหรือโค้ดที่ทำได้จริง | แอปเขียนสัญญาไว้แต่ยังไม่มีฟีเจอร์รองรับ = ความเสี่ยงกฎหมาย |
| 4 เดินแบบ persona | เบราว์เซอร์ขนาดมือถือ · เข้าครั้งแรก → จุดว้าว → ใช้ทุกแท็บ · **ต้องกดจริง ไม่ใช่อ่านโค้ดแทน** · ในแต่ละหน้าถาม 5 ข้อ: **(ก)** ใส่ข้อมูลอะไร แล้วข้อมูลนั้นไปแสดงที่ไหน (ถ้าไม่ไปไหนเลย = ข้อมูลกรอกแล้วสูญเปล่า) **(ข)** หน้าว่างพาไปทำอะไรต่อ **(ค)** มีทางตันไหม **(ง)** ทุกตัวเลือกกดแล้วมีผลจริงไหม **(จ)** เมื่อเวลาเปลี่ยน (ยังไม่เริ่ม / วันที่ไม่มีอะไรต้องทำ / หลังจบ) หน้าจอบอกไหมว่าต้องทำอะไรต่อและเมื่อไหร่ · วัดจุด 2.1–2.4 ระหว่างเดิน | เห็นว่ามีปุ่มแล้วคิดว่าทำงาน · บันทึกลง DB ได้แล้วคิดว่าจบ · ลองแค่สถานะของวันนี้ |
| 5 ขอบ ทางแตก และความปลอดภัย | วันที่ในอดีต / อนาคต / ข้ามเที่ยงคืนตามเขตเวลา · ค่าว่าง / 0 / ค่าติดลบ · **แตะรัว 3 ครั้ง** · เน็ตช้าหรือหลุด · error ที่ไม่ใช่ `Error` แสดงเป็นอะไรบนจอ · **ความปลอดภัยแบบเร็ว 3 ข้อ:** (1) grep `NEXT_PUBLIC_` แล้วดูว่ามีความลับหลุดไปฝั่งเบราว์เซอร์ไหม (2) policy UPDATE แก้คอลัมน์สิทธิ์ของตัวเองได้ไหม (`role`, `plan`, `is_admin`) (3) มีผู้ใช้คนเดียว → ใช้ transaction แบบอ่านอย่างเดียว (`set local role authenticated` + `set local request.jwt.claims`) แล้ว select ข้อมูลของ uid อื่น | ทดสอบแค่ข้อมูลของวันนี้ · ข้ามเรื่องความปลอดภัยเพราะ "ไม่ใช่งาน QA" |
| 6 ความรู้สึกขณะใช้ | วัดอาการกระพริบหรือค้างด้วย `probes.js` (`traceNav` ใช้ได้ทั้งลิงก์และปุ่มแท็บ, `timeToChange`) · ดูคอนโซลว่ามี error ไหม **หลังรีโหลดใหม่หมด** (error เก่าอาจค้างจาก hot reload) | ใช้สายตาดูอย่างเดียวว่า "ลื่นแล้ว" |
| 7 ดีไซน์สม่ำเสมอ | จุด 1.1–1.4 · ค้นในโค้ดและวัดค่า computed style ข้ามหน้า (สี ขนาดตัวอักษร ระยะห่าง ปุ่ม) | กวาดตาแล้วบอกว่า "ดูเข้ากันดี" |
| 8 เข้าใจทันทีไหม | จุด 5.1–5.4 · 5.1 ส่ง sub-agent ที่ไม่มีบริบท 1 ตัว ให้ดูแค่ภาพ/ข้อความหน้าแรก แล้วตอบ 3 ข้อ: เว็บทำอะไร · ให้ใคร · ควรกดอะไรต่อ → เทียบกับเป้าที่ตั้งใจ | ข้าเขียนเว็บเองจึงรู้คำตอบอยู่แล้ว ทดสอบความชัดเองไม่ได้ |

## เช็กลิสต์ 20 จุด (5 ด้าน · ทุกจุดต้องวัดหรือกดจริง)

| ด้าน | จุด |
|---|---|
| 1 ดีไซน์ | 1.1 สีทุกจุดมาจากชุดสีกลาง ไม่มีโค้ดสีลอยนอก token · 1.2 ขนาดตัวอักษร ≤6 ระดับ ฟอนต์ชุดเดียว · 1.3 ระยะห่างเป็นสเกลเดียวกันทุกหน้า · 1.4 ปุ่มชนิดเดียวกันหน้าตาเหมือนกันทุกหน้า และปุ่มหลักหน้าละ 1 |
| 2 มือถือ | 2.1 จอ 375px ไม่เลื่อนแนวนอน (`scrollWidth` ≤ `clientWidth`) · 2.2 ปุ่มและลิงก์สูง ≥44px · 2.3 เมนูเปิดปิดได้และพาไปครบทุกหน้า · 2.4 ช่องกรอกเรียกคีย์บอร์ดถูกชนิด ตัวอักษร ≥16px และคีย์บอร์ดไม่บังปุ่ม |
| 3 สถานะ | 3.1 กำลังโหลด · 3.2 ไม่มีข้อมูล บอกว่าทำอะไรต่อ · 3.3 กรอกผิด บอกช่องไหน ผิดยังไง ข้อมูลที่กรอกยังอยู่ · 3.4 ระบบล้ม บอกหลุดขั้นไหน เสียเงินหรือข้อมูลไหม และทางออก |
| 4 ใช้งานจริง | 4.1 คนใหม่เดินจากหน้าแรกจนจบงานหลัก · 4.2 ทุกลิงก์และปุ่มมีปลายทาง · 4.3 ข้อมูลที่กรอกแสดงกลับให้เห็น · 4.4 คำสัญญาบนจอมีฟีเจอร์รองรับ |
| 5 ก่อนเปิดเว็บ | 5.1 ทดสอบ 5 วินาทีผ่าน (ชั้น 8) · 5.2 แต่ละหน้ามีเป้าหมายเดียว · 5.3 คำบนจอเป็นภาษาคน ไม่มีศัพท์ dev ไม่มี `—` `→` · 5.4 ชื่อหน้า คำอธิบาย ภาพตอนแชร์ลิงก์ ไอคอน หน้า privacy/terms และช่องทางติดต่อครบ |

**เสร็จเมื่อ:** ทั้ง 20 จุดมีสถานะ ✅ ผ่าน / ❌ ไม่ผ่าน / ⏭ ไม่ได้ตรวจ และทุกสถานะมีหลักฐานหรือเหตุผลกำกับ

## ข้อมูลทดสอบ (บังคับ)
- จดค่าเดิมไว้ก่อนแก้ → ทดสอบ → คืนค่าผ่าน **ทางเดียวกับที่ผู้ใช้ทำ** → query ยืนยันว่าไม่มีแถวค้าง
- ห้ามลบข้อมูลจริง · ปุ่มลบให้ทดสอบแค่ขั้นยืนยัน เว้นแต่ข้อมูลนั้นสร้างขึ้นเพื่อทดสอบเอง
- **แอปไม่มีทางลบคืน** (เช่น ไม่มีปุ่มลบผลเลือด) หรือมีแถวที่ระบบเพิ่มเอง (event log) → ยังต้องทดสอบ แต่จด id ของแถวที่สร้างไว้ในรายงานหัวข้อ "ข้อมูลที่ค้างจากการทดสอบ" ให้เจ้าของเป็นคนตัดสินว่าจะลบหรือไม่ · การไม่มีทางลบคืน ถือเป็นข้อค้นพบในชั้น 2 ด้วย
- ถ้าสร้างผู้ใช้ใหม่ไม่ได้ ให้เปิดหน้า first-run ตรงๆ และเขียนในรายงานว่าไม่ได้เดินจากบัญชีใหม่จริง

## รายงาน (รูปแบบเดียวทุกครั้ง)
1. **เช็กลิสต์ 20 จุด** ✅/❌/⏭ + หลักฐานหรือเหตุผลสั้นๆ ต่อจุด
2. ภาพเส้นทางผู้ใช้ + ความรู้สึกในแต่ละหน้า (ASCII)
3. ส่วนที่ใช้งานได้และมีประโยชน์จริง
4. ตาราง `# | ด้าน | หน้า | สิ่งที่เจอ | หลักฐาน | ผลต่อผู้ใช้ | แนะนำ` เรียง **P0** (ข้อมูลผิด / ผิดกฎหมาย / สัญญาไว้แต่ทำไม่ได้) → **P1** (คนเลิกใช้) → **P2** (น่ารำคาญ) · หลักฐาน = ภาพหน้าจอ ค่าที่วัด หรือ file:line
5. **สิ่งที่ไม่ได้ทดสอบ พร้อมเหตุผล** ห้ามละส่วนนี้
6. ข้อมูลที่ค้างจากการทดสอบ (ถ้ามี)
7. ปิดท้ายด้วยคำถามเดียว: ท่านจะให้แก้ข้อไหน

ถ้าปัญหามีมาก ให้เก็บทุกข้อไว้ในตาราง แต่เขียนแต่ละข้อให้สั้นลง ห้ามตัดข้อ P0 ออก

## เรียกสกิลอื่นตามจังหวะ (ไม่เขียนซ้ำ)
- เจอบั๊ก → `ego-avatar:diagnosing-bugs`
- ด่านก่อนบอกว่าเสร็จ → `superpowers:verification-before-completion`
- ชั้น 5 เรื่องสิทธิ์และ auth → `security-review`
- ชั้น 4 มุม activation → `marketing-skills:onboarding` · การเข้าถึง → `design:accessibility-review`
- ชั้น 7 เจอดีไซน์แตกหลายจุด → `ego-avatar:hallmark` (audit) · ชั้น 8 หน้าแรกไม่ชัด → `marketing-skills:copywriting` / `marketing-skills:cro`

## ข้ออ้างที่ต้องหยุดทันที

| ข้ออ้าง | ความจริง |
|---|---|
| "ทดสอบส่วนที่แก้แล้ว" | ส่วนที่ไม่ได้แก้ก็พังได้ และช่องว่างระหว่างฟีเจอร์ไม่มีใครแก้ |
| "มีปุ่มนี้แล้ว" | ต้องกดแล้วตามไปดูผลปลายทาง |
| "บันทึกลง DB ได้" | ผู้ใช้ได้เห็นข้อมูลนั้นกลับมาที่ไหน |
| "error พวกนั้นมีอยู่ก่อนแล้ว" | พิสูจน์ด้วยการรัน baseline ก่อน |
| "สร้าง user ใหม่ไม่ได้ ข้าม first-run ไป" | เปิดหน้า first-run ตรงๆ แล้วเขียนในรายงานว่ามีข้อจำกัดนี้ |
| "ดูแล้วลื่น" / "ดูเข้ากันดี" | วัดเป็นตัวเลข: มิลลิวินาที · px · จำนวนค่าสีที่ต่างกัน |
| "ไม่กดบันทึกจริง กลัวข้อมูลเปลี่ยน" | อ่านโค้ดไม่เจอบั๊กจากการแตะรัว · ให้ทดสอบจริงแล้วจดแถวที่ค้างไว้ในรายงาน |
| "ความปลอดภัยไม่ใช่งาน QA" | ความลับหลุดไปฝั่งเบราว์เซอร์ต้องจับให้ได้ก่อนปล่อย · ใช้แค่ 3 ข้อในชั้น 5 |
| "เจอแล้วแก้ไปเลย เร็วกว่า" | รายงานก่อน ท่านเลือกข้อ · บางข้อท่านตั้งใจให้เป็นแบบนั้น |
| "หน้าแรกชัดอยู่แล้ว ข้าอ่านเข้าใจ" | ข้าคือคนเขียน · ใช้ sub-agent ที่ไม่มีบริบทตอบแทน |
